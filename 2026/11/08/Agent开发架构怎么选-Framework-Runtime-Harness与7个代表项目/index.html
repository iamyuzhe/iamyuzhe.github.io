Agent 开发架构怎么选：Framework、Runtime、Harness 与 7 个代表项目

发表于 2026-11-08 分类于 ai-engineering 阅读次数：
根据 AI 产品千媚的视频，梳理 Agent Framework、Runtime、Harness 的边界，对比 7 个代表项目，并给出插件、SDK 与源码改造三层选型方法。

开发一个 Agent，最先要决定的往往不是模型，而是从哪一层开始搭建：

起点选得太低，团队会重复实现上下文、权限、文件、会话和恢复机制；起点选得太高，又可能发现关键流程被封装，业务差异无法落地。

这篇文章整理自 AI 产品千媚的视频 《Agent 开发架构怎么选？7 个代表项目系统对比》。视频比较了 Claude Agent SDK、Deep Agents、Pi、OpenCode、OpenClaw、Hermes Agent 和 DeepSeek Harness，并用“默认实现了多少机制”和“开放了多少控制权”两条轴解释选型差异。[cite:1]

一、先区分 Framework、Runtime 与 Harness

这三个词经常混用，但它们解决的问题并不相同。

Framework：提供构建模块

Framework 主要负责把模型、工具、提示词和流程节点连接起来。开发者通常可以自由设计：

  • 模型如何接收上下文；
  • 工具如何注册和调用；
  • 多个步骤如何连接；
  • 不同 Agent 如何协作；
  • 业务状态如何在节点间传递。

Framework 的优势是灵活，代价是大量基础机制仍要自己补齐。工具权限、上下文压缩、任务恢复、文件系统、会话持久化、审计和评测，通常不会因为“已经能调用工具”就自动成立。

Runtime：保证流程能够持续执行

Runtime 更关注执行过程：

  • 状态保存与恢复；
  • 长任务和中断续跑；
  • 事件流与流式输出；
  • 并发和任务调度；
  • 人工审批；
  • 错误重试与检查点。

它回答的是“这条流程怎样可靠地跑下去”，而不一定替开发者决定 Agent 应该拥有哪些工具、记忆和工作方式。

Harness：提供完整的执行系统

Harness 位于更高层。它通常把模型、工具、上下文、Agent Loop、文件系统、权限、会话、记忆、子 Agent、Skills 和可观测性组合成一套可直接使用的执行系统。

视频把技术演进概括为从 Framework、Runtime 到 Harness。这个时间线适合帮助理解开发起点的变化，但不是严格的行业分期：很多项目同时跨越多层，边界也会随版本演进而变化。[cite:1]

二、Harness 解决的不是一次工具调用

一个简单 Agent 可能只需要：

但真实业务很快会出现更多要求：

  • 某一步失败后从哪里重试；
  • 长结果是否写入文件而不是塞回上下文；
  • 哪些工具可以自动执行，哪些必须审批；
  • 如何避免 Agent 反复调用同一个工具；
  • 会话怎样恢复；
  • 多个子任务怎样隔离上下文；
  • 运行轨迹怎样审计；
  • 模型切换后行为是否退化。

课程用“研究一家公司的产品”说明了同一个目标可能需要搜索资料、验证关键信息、编写代码分析数据，再根据中间结果继续迭代。真正复杂的不是某个工具，而是工具之间的组织、状态、边界和恢复。[cite:1]

因此，选 Harness 时不应只看工具数量，而应该看它默认替团队解决了多少执行问题。

三、两条选型轴：默认机制与控制权

视频采用了两个很实用的比较维度：

默认实现了多少机制

默认机制越多，通常意味着更快启动：

  • 内置 Agent Loop；
  • 文件读写和命令执行；
  • 上下文管理与压缩；
  • 会话与恢复；
  • 权限和 Hook；
  • 子 Agent；
  • Skills、记忆与计划；
  • 日志和运行轨迹。

但默认机制越多，也意味着团队要先理解项目预设的工作方式。

开放了多少控制权

控制权关注的是：

  • 能否替换模型、工具和存储；
  • 能否控制上下文进入方式；
  • 能否改变循环和停止条件；
  • 能否插入审批、审计与策略；
  • 能否替换执行环境；
  • 能否把核心机制嵌入自己的产品。

这两条轴并不是简单的“功能多”和“功能少”。一个项目可以同时拥有丰富默认能力和较强扩展性，只是学习成本和改造边界不同。

四、七个代表项目的定位

1. Claude Agent SDK：复用 Claude Code 的执行系统

Claude Agent SDK 将 Claude Code 的 Agent Loop、上下文管理和工具能力封装为 Python 与 TypeScript 库。官方列出的能力包括内置工具、Hooks、子 Agent、MCP、权限、会话、Skills、记忆和插件。[cite:2]

它适合：

  • 希望快速得到成熟 Agent 执行能力；
  • 业务能够接受 Claude Code 的核心工作方式；
  • 需要通过 Hook 增加审批、审计或业务规则；
  • 希望把 Agent 嵌入现有 Python 或 TypeScript 服务。

它的关键价值不是“调用 Claude API 更方便”，而是直接复用已经形成的 Agent Harness。与普通 Client SDK 相比，开发者不需要重新实现完整工具循环。

需要注意的是，复用成熟 Loop 也意味着底层执行哲学已有明确预设。如果业务必须彻底改变循环、上下文策略或模型选择边界，需要先确认 SDK 暴露的扩展点是否足够。

2. Deep Agents：默认完整，同时强调模块化

Deep Agents 在 LangChain 和 LangGraph 之上提供面向复杂多步任务的 Harness。官方能力包括计划、虚拟文件系统、上下文管理、长期记忆、子 Agent、人工审批和可插拔 Backend。[cite:3]

它适合：

  • 研究、数据分析、文档处理等综合任务；
  • 需要模型和工具供应商选择空间；
  • 需要自定义文件或执行 Backend；
  • 既希望有完整默认能力，又希望通过 Middleware 调整行为。

Deep Agents 的特点是“默认完整，但仍保留模块化入口”。例如，虚拟文件系统可以映射到内存、本地磁盘、持久化 Store 或自定义 Backend；子 Agent 可以隔离长任务上下文；Middleware 可以替换或扩展特定能力。[cite:3]

代价是系统层次较多。团队需要理解 LangChain、LangGraph、Middleware、Backend 与 Deep Agents Harness 之间的职责，否则容易在错误层次修改问题。

3. Pi：保持核心极简，把选择权交给开发者

Pi 将自己定义为 minimal agent harness。它提供基本 Coding Agent 能力、会话树、上下文压缩、Skills、扩展、RPC 和 SDK，但有意不把子 Agent、Plan Mode、权限弹窗等工作方式写死在核心中。[cite:4]

它适合：

  • 希望精确控制上下文和工具；
  • 不认同现成 Coding Agent 的默认流程；
  • 愿意通过 TypeScript Extension 构建能力；
  • 希望将极简核心嵌入自己的产品。

Pi 的思路是“提供 primitives，而不是预设所有 features”。扩展可以访问工具、命令、事件、键盘交互和 TUI，因此团队能够构建自己的权限门、计划模式、沙箱、SSH 执行或子 Agent。[cite:4]

这种自由度的代价很明确：缺少的默认机制不会凭空出现。安全、审批、任务恢复、并发和观测需要由团队选择插件、编写扩展或在外层补齐。

4. OpenCode：围绕软件开发提供完整工作流

OpenCode 面向软件开发场景，内置 Build、Plan、General、Explore 等角色。Build 可以执行文件修改和系统命令，Plan 默认限制写操作，General 与 Explore 则分别承担通用多步任务和只读代码探索。[cite:5]

它适合：

  • 目标明确是代码探索、修改、执行和验证；
  • 希望直接获得角色分工和权限边界；
  • 需要通过配置定义模型、提示词、工具权限和子 Agent；
  • 不想从零搭建 Coding Agent 交互流程。

OpenCode 的优势是完整的软件开发产品形态。视频将它与 Pi 对比：Pi 更像可自由设计执行方式的极简核心，OpenCode 则已经替用户定义了更完整的开发路径。[cite:1]

如果业务目标不是 Coding Agent，直接改造 OpenCode 可能不如从更通用的 SDK 或极简 Harness 出发。

5. OpenClaw：以 Gateway 连接个人工作入口

OpenClaw 的重点不只在 Agent Loop，而在 Gateway。它可以连接多种消息渠道，并围绕会话、记忆、多 Agent 路由、Skills、插件、定时任务和 Webhook 形成个人助手的管理中心。[cite:6]

它适合：

  • 从飞书、Slack、Telegram、WhatsApp 等入口接收任务；
  • 需要持续在线的个人或团队助手；
  • 需要定时任务、Webhook 和跨渠道投递；
  • 希望把 Agent 作为长期运行的服务，而不是一次 CLI 调用。

这类系统的核心复杂度是“入口与运行治理”：身份、会话归属、渠道路由、长期记忆、权限和自动化都比单次推理更重要。

6. Hermes Agent：强调持续学习与能力沉淀

Hermes Agent 同样提供消息渠道、持久记忆、定时任务、子 Agent 和 Skills，但官方定位特别强调闭环学习：Agent 可以从经验中创建 Skills，在使用过程中改进，并把跨会话信息沉淀为可复用能力。[cite:7]

它适合：

  • Agent 会长期服务同一用户或团队；
  • 需要把重复任务沉淀成 Skills；
  • 希望记忆、用户模型和自动化共同演进；
  • 需要在本地、容器、SSH 或云端执行环境间切换。

视频用“写周报”举例：Agent 不只完成一次周报，还能总结方法、保存为 Skill，并在后续任务中直接复用。[cite:1]

这类“持续学习”需要更严格的治理。错误经验如果未经评测就固化为记忆或 Skill，长期影响可能比一次错误回答更大。

7. DeepSeek Harness：连核心机制也插件化

DeepSeek Harness 采用 “Everything is a plugin” 架构。模型、工具、Skills、会话、沙箱、存储、Agent Loop、调度和 UI 都可以作为插件组合或替换。[cite:8]

它适合：

  • 研究不同 Agent Loop；
  • 构建自己的 Harness 平台；
  • 希望替换核心执行机制；
  • 需要完整运行轨迹、恢复、分叉和回放。

官方还提供 Standard、Code、Minimal 和 Creator 等运行模式，并通过追加写 Session Log 记录模型看到的提示词、推理、工具调用、子 Agent 调度和上下文注入。[cite:8]

这带来很高的可塑性，也带来更高的系统责任。DeepSeek Harness 目前仍处于 Developer Preview，核心 API 和插件接口可能继续变化，生产采用时必须评估升级和兼容成本。[cite:8]

五、不要按“综合任务”和“编码任务”画死边界

视频先把项目粗略分为综合任务类与编码类：

粗略类型 代表项目 默认优化方向
综合任务 Claude Agent SDK、Deep Agents 研究、数据分析、文档处理、代码执行
编码任务 Pi、OpenCode 代码探索、文件修改、命令执行、测试验证
个人助手与长期运行 OpenClaw、Hermes Agent 多渠道、记忆、自动化、持续任务
Harness 平台 DeepSeek Harness 核心机制组合、替换和实验

但分类不等于严格边界。Claude Agent SDK 来自 Claude Code，却可以构建非编码 Agent；Pi 可以通过 Extension 发展成个人工作流；OpenClaw 可以把其他 Coding Harness 作为执行后端；DeepSeek Harness 也提供完整 Coding Agent 模式。

六、七个项目的横向比较

下面的表格综合视频观点与各项目官方文档。它描述的是架构倾向，不是性能排名。

项目 默认完整度 控制方式 更适合的起点 主要代价
Claude Agent SDK 高 Hooks、工具、权限、插件、SDK 配置 快速复用成熟 Agent Loop 核心执行方式已有较强预设
Deep Agents 高 Middleware、Backend、模型与工具配置 综合任务与可定制执行环境 需要理解多层抽象
Pi 较低 Extension、Skill、RPC、SDK 极简 Coding Agent 与自定义工作流 大量机制需要自行选择或实现
OpenCode 高 Agent 配置、Prompt、模型、细粒度权限 完整软件开发流程 非编码场景可能需要逆向改造
OpenClaw 高 Gateway、插件、渠道、Agent 路由 多渠道个人或团队助手 部署与权限治理复杂
Hermes Agent 高 Skills、记忆、Bot、Gateway、Backend 长期运行和持续学习 学习闭环需要评测与纠错
DeepSeek Harness 中到高 几乎所有机制插件化 Harness 研究和平台开发 Preview 阶段，集成责任较大

如果只看功能清单，这些项目会显得越来越相似。更有区分度的问题是：

  • Agent Loop 能否改变；
  • 上下文和状态由谁管理；
  • 工具执行发生在哪里；
  • 权限在什么层生效；
  • 持久化格式能否迁移；
  • 运行轨迹能否审计和回放；
  • 业务需要承担多少基础设施责任。

七、用三层需求决定改造方式

视频最后把开发需求拆成三个层次，这比直接比较项目 Star 数更实用。

第一层：扩展现有 Agent

如果已有 Agent 产品，只需要增加：

  • 一个工具；
  • 一套固定工作流；
  • 领域知识；
  • 自动化命令；
  • 特定审批规则。

优先选择：

以 Pi 为例，可以通过 Extension 增加自动检查、按要求生成 PR 描述或新的工具；产品仍然是 Pi，只是能力被扩展。[cite:1][cite:4]

这一层不应轻易 Fork 源码。插件边界通常更容易升级、测试和移除。

第二层：开发自己的 Agent 产品

如果需要自己的界面、用户体系、任务系统和业务流程，但不想重写 Agent Loop，可以采用：

这时产品属于自己，底层复用 Claude Agent SDK、Deep Agents 或 Pi SDK 等执行能力。重点是确认：

  • SDK 是否支持目标语言；
  • 会话能否外部持久化；
  • 事件是否可流式消费；
  • 工具与权限是否可注入；
  • 是否支持取消、恢复和并发；
  • 授权与商业条款是否匹配。

第三层：改造底层 Harness

只有当需求涉及下面这些问题时，才应该进入源码或核心插件层：

  • 改变 Agent Loop；
  • 替换调度或上下文机制；
  • 研究新的工具编排方式；
  • 构建 Harness 平台；
  • 对运行轨迹和恢复机制有特殊要求。

此时可以选择 DeepSeek Harness 这类核心机制可替换的系统，或 Fork 一个足够小、足够清楚的代码库。

代价不只是初次开发，还包括：

  • 跟进上游安全修复；
  • 维护模型和工具协议变化；
  • 处理状态格式迁移；
  • 建立兼容测试；
  • 为团队提供调试和观测工具。

八、一套可执行的选型流程

1. 先写业务闭环

不要先列框架名称。先画出真实任务：

2. 标记不可妥协的控制点

例如：

  • 模型必须可替换；
  • 工具必须运行在内网沙箱；
  • 所有写操作必须审批；
  • 会话必须存储在自有数据库；
  • 运行轨迹必须可审计；
  • 必须支持飞书入口；
  • 必须允许自定义 Agent Loop。

这些要求会直接排除不合适的抽象层。

3. 选择最高可接受起点

一个实用原则是：

在不失去关键控制权的前提下，选择能够复用最多成熟机制的最高层起点。

这样可以减少重复建设，但不会把业务差异埋在无法修改的黑盒中。

4. 用同一条任务做小型验证

不要只跑“查询天气”Demo。选一条接近生产的任务，至少验证：

  • 多步工具调用；
  • 长上下文；
  • 文件读写；
  • 权限拒绝；
  • 中断和恢复；
  • 错误重试；
  • 日志与轨迹；
  • 模型切换；
  • 任务成功标准。

5. 评估升级而不只是开发

PoC 能跑通不代表长期成本可控。还要检查：

  • 上游发布节奏；
  • 配置和状态格式是否稳定；
  • 扩展点是否有兼容承诺；
  • 核心能力是否依赖单一模型；
  • Fork 后与上游同步的成本；
  • 团队能否定位 Harness 内部问题。

九、不同目标下的推荐起点

目标 优先考察
尽快获得成熟的通用 Agent 执行能力 Claude Agent SDK
综合任务，且需要 Backend、模型与 Middleware 定制 Deep Agents
构建极简、强定制的 Coding Agent Pi
直接使用完整的软件开发工作流 OpenCode
从多个聊天渠道运营长期个人助手 OpenClaw
让记忆与 Skills 随长期使用持续沉淀 Hermes Agent
研究或搭建可替换核心机制的 Harness 平台 DeepSeek Harness

组合的前提是明确每一层的状态所有权、身份边界和失败责任。

十、生产环境还要补齐的能力

视频重点讨论开发起点和控制权。进入生产环境后，还要单独评估：

  • Prompt Injection 与工具输入校验；
  • 文件、网络和命令沙箱；
  • 用户身份与租户隔离；
  • 凭据管理；
  • 人工审批和紧急停止；
  • 幂等、重试和补偿；
  • Token、时延与工具成本；
  • 运行轨迹、指标和告警；
  • 离线评测与线上回归；
  • 记忆和 Skill 的纠错与删除。

Harness 可以提供这些机制的起点，但不会自动替业务定义安全策略和成功标准。

总结

Agent 架构选型的核心，不是找“功能最多”的项目，而是确定团队真正需要控制哪一层。

Claude Agent SDK 和 Deep Agents 倾向于让团队快速复用完整执行能力；Pi 用极简核心换取控制权；OpenCode 围绕软件开发提供完整产品工作流；OpenClaw 与 Hermes Agent 面向长期运行的个人助手；DeepSeek Harness 则把 Harness 本身变成可组合和替换的开发平台。

更稳妥的决策方式是：先画出业务闭环，标记不可妥协的控制点，再选择最高可接受的抽象层。复用成熟能力可以节省大量工程成本，但任何被复用的默认机制，都应该先经过真实任务、权限边界和恢复路径的验证。
