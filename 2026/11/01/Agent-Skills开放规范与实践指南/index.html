Agent Skills：让 AI Agent 获得可复用能力的开放规范

发表于 2026-11-01 分类于 artificial intelligence 阅读次数：
从开放规范、技能创建、触发优化、质量评估、脚本设计和客户端接入六个方面，系统理解 Agent Skills。

大语言模型具备广泛的通用能力，但真正进入工程环境后，往往还缺少三类关键上下文：

  • 团队实际采用的工具、接口和约束；
  • 一个任务可靠完成所需的操作顺序；
  • 从历史故障、评审意见和项目实践中积累的隐性经验。

Agent Skills 提供了一种轻量、开放的解决方案：把专业知识、工作流程和配套资源组织成可被 AI Agent 按需加载的目录。它不是新的模型，也不是一套重量级插件系统，而是一种以 SKILL.md 为核心的能力封装格式。[cite:1]

一、Agent Skills 是什么

一个最小的 Agent Skill 只是一个目录和其中的 SKILL.md 文件：

其中：

  • SKILL.md 是唯一必需文件，包含元数据和执行说明；
  • scripts/ 放置可重复执行的脚本；
  • references/ 保存按需读取的详细资料；
  • assets/ 保存模板、图片、Schema 或其他静态资源。

这种形式有几个直接价值：

  1. 可复用：一次整理的流程可以反复用于同类任务。
  2. 可审查：技能内容是普通文件，可以进入版本控制和代码评审。
  3. 可移植：遵循同一格式的技能可以被不同 Agent 客户端识别。
  4. 可组合：每个技能聚焦一个连贯的工作单元，复杂任务可以组合多个技能完成。

Agent Skills 最早由 Anthropic 开发并开放，随后逐渐被更多 Agent 产品采用。[cite:1][cite:9]

二、核心机制：渐进式披露

如果 Agent 在启动时读取所有技能的完整内容，大量无关说明会占满上下文窗口。Agent Skills 用“渐进式披露”解决这个问题，将加载过程分成三层：[cite:1][cite:2]

层级 加载内容 加载时机
技能目录 name 和 description 会话开始时
完整说明 SKILL.md 正文 技能与当前任务匹配时
配套资源 脚本、参考资料、模板 执行过程中确有需要时

这意味着 Agent 可以知道“有哪些能力可用”，却不必提前承担全部上下文成本。一个客户端即使安装了几十个技能，当前会话通常也只会加载真正相关的几个。

该机制也解释了为什么 description 如此重要：在技能正文尚未加载时，它几乎独自承担了技能发现和触发的职责。

三、SKILL.md 的格式规范

SKILL.md 由 YAML Front Matter 和 Markdown 正文组成：

必需字段

字段 作用 主要约束
name 技能唯一名称 最长 64 个字符；使用小写字母、数字和连字符；与目录名一致
description 能力范围和触发条件 非空，最长 1024 个字符

可选字段

字段 用途
license 声明许可证或指向许可证文件
compatibility 描述运行环境、系统依赖或网络要求
metadata 保存作者、版本等自定义字符串元数据
allowed-tools 声明预批准工具，目前仍属于实验字段

规范建议让主 SKILL.md 保持在 500 行、5000 tokens 以内。更详细的 API 文档、错误码、模板和长示例应该拆入 references/ 或 assets/，并在正文中明确说明何时读取。[cite:2]

  2. 判断请求与描述匹配，加载完整 SKILL.md；

五、怎样写出有效的技能

从真实经验中提炼

最常见的误区，是让模型仅凭通用知识生成一个看似完整的技能。这样的技能通常充满“妥善处理异常”“遵循最佳实践”等正确但无用的表述。

高价值技能应来自真实材料：

  • 已经成功完成的任务及其操作顺序；
  • 用户或评审者曾经给出的纠正；
  • 项目 Runbook、接口规范和配置文件；
  • Code Review 评论、Issue 和历史修复；
  • 真实故障及其恢复过程。

如果某条说明不能降低 Agent 犯错的概率，它通常就不值得占用上下文。

控制技能边界

技能边界类似函数职责：

  • 太窄，会让一个任务被拆成大量微型技能，增加加载和协调成本；
  • 太宽，会导致触发条件模糊，正文中充斥与当前任务无关的分支。

合适的技能应该覆盖一个完整、连贯、可以独立验证的工作单元。例如“查询数据库并格式化结果”可以是一个技能，而把数据库管理、备份、迁移和性能调优全部塞进去通常过于宽泛。

根据任务风险调整控制强度

并非所有步骤都需要同样严格：

  • 对代码评审、方案分析等开放任务，说明目标、关注点和原因，允许 Agent 根据上下文选择方法；
  • 对数据库迁移、生产发布等脆弱任务，给出明确顺序、固定命令、验证门禁和停止条件；
  • 多个方案都可行时，提供一个默认方案，再简要说明何时使用替代方案。

使用高价值结构

实践中最有效的几类结构包括：

  • Gotchas：记录违反直觉、容易反复踩坑的事实；
  • 输出模板：直接展示期望结构，而不是只用文字描述；
  • 检查清单：帮助 Agent 跟踪多阶段工作；
  • 验证循环：执行、验证、修复，再次验证；
  • Plan-Validate-Execute：批量或破坏性操作先生成计划并校验，再执行；
  • 配套脚本：把每次都会重写的确定性逻辑固化为程序。

这些内容比泛泛的背景知识更能提升执行稳定性。[cite:4]

六、让技能在正确的时机触发

一个技能即使正文写得很好，如果无法在正确请求上触发，也不会产生价值。优化描述时需要同时控制两类错误：

  • 漏触发：相关请求没有加载技能；
  • 误触发：无关或仅关键词相似的请求加载了技能。

描述的写法

有效描述应做到：

  1. 从用户意图出发，而不是描述内部实现；
  2. 同时说明“做什么”和“什么时候使用”；
  3. 包含用户可能使用的文件类型、领域词和任务表达；
  4. 保持简洁，不把正文内容复制到描述里。

例如：

用正反样本测试

官方建议准备约 20 条触发测试，其中正例和反例各 8 到 10 条。好的测试集不应只包含明显样本，还要包含：

  • 不同语气、长度和详细程度的请求；
  • 没有明确说出领域名称、但确实需要该技能的请求；
  • 与技能共享关键词、实际意图却不同的“近似反例”；
  • 文件路径、字段名、缩写和少量拼写错误等真实上下文。

由于模型行为存在随机性，同一查询应运行多次并统计触发率。还应将样本固定划分为训练集和验证集，避免为了通过已知样本而过度拟合描述。[cite:5]

七、评估技能是否真正提高质量

“成功触发”只说明技能被加载，并不说明输出更好。质量评估需要将同一任务分别在“启用技能”和“未启用技能”条件下运行，比较结果、时间和 token 成本。[cite:6]

定义测试用例

一个测试用例至少包含：

初期只需要 2 到 3 个真实用例，观察输出后再补充断言。断言必须具体、可验证，例如：

  • 生成了图片文件；
  • 图表恰好包含三个月份；
  • 两个坐标轴都有标签；
  • 标题或说明包含“收入”。

“输出很好”无法验证，而要求输出必须出现某句固定文案又过于脆弱。

记录证据和成本

每条断言都应该记录 PASS 或 FAIL 以及具体证据。除了通过率，还应记录：

  • 总 token 数；
  • 执行耗时；
  • 产生的文件；
  • 人工评审反馈；
  • 完整执行轨迹。

执行轨迹尤其重要。它能解释问题来自哪里：说明太模糊、无关步骤太多、脚本接口不清晰，还是技能本身没有提供模型缺失的知识。

迭代闭环

一个完整循环是：

  1. 使用技能和基线分别运行测试；
  2. 根据断言和人工反馈评分；
  3. 阅读执行轨迹，找到失败原因；
  4. 修改描述、流程、示例或脚本；
  5. 在新迭代目录中重新运行全部测试；
  6. 对比质量收益与时间、token 成本。

当失败反馈持续为空，或者后续迭代已经没有明显收益时，技能才算进入相对稳定状态。

八、何时在技能中使用脚本

语言模型擅长理解意图和处理开放问题，脚本擅长确定性计算、解析和验证。两者结合通常比纯提示词更可靠。

一次性命令

如果现有工具已经解决问题，可以直接在 SKILL.md 中给出固定版本命令：

固定版本能够减少工具升级带来的行为漂移。命令过长、参数组合复杂或每次都容易写错时，应移入 scripts/。

可复用脚本

适合脚本化的工作包括：

  • 解析固定格式；
  • 生成图表或文档；
  • 校验配置和输出；
  • 执行可重复的数据转换；
  • 实现 dry-run 和变更计划。

面向 Agent 的脚本还应具备以下特征：

  • 不依赖交互式输入；
  • 提供简洁明确的 --help；
  • 错误消息说明原因、期望值和修复方法；
  • 标准输出使用 JSON、CSV 等结构化格式；
  • 诊断信息写入标准错误；
  • 操作尽量幂等；
  • 破坏性操作提供 --dry-run 或显式确认参数；
  • 控制默认输出长度，避免工具结果被截断。

脚本不仅是实现细节，它还是 Agent 与确定性系统之间的接口。[cite:7]

九、Agent 客户端怎样支持 Skills

对于 Agent 或开发工具的实现者，完整生命周期包括发现、解析、披露、激活和上下文管理。[cite:8]

1. 发现

本地客户端通常同时扫描项目级和用户级目录：

也可以兼容客户端自己的目录。发生同名冲突时，一般让项目级技能覆盖用户级技能，并输出可诊断的警告。来自陌生仓库的项目级技能可能包含不受信任的指令，因此应与工作区信任机制结合。

2. 解析

客户端读取 YAML Front Matter，至少保存：

  • name
  • description
  • SKILL.md 的位置

缺少描述或 YAML 完全无法解析时应跳过；目录名不匹配等非关键问题可以警告后继续加载，以兼顾规范和跨客户端兼容性。

3. 披露

客户端只把技能目录提供给模型，可以放在系统提示词中，也可以放在专用激活工具的描述里。目录应简洁，并明确告诉模型如何加载完整技能。

4. 激活

常见方式有两种：

  • 模型使用文件读取工具打开 SKILL.md；
  • 模型调用 activate_skill(name) 等专用工具。

专用工具可以附带技能根目录和资源清单，但不应一次性读取所有资源。用户还应该能够通过 /skill-name 或 $skill-name 等方式显式激活技能。

5. 上下文管理

技能激活后，其说明属于当前任务的持续行为约束。若客户端会压缩长对话，应保护技能内容不被随意裁剪，并避免在同一会话中重复注入同一个技能。

十、从零到可维护技能的实践清单

创建阶段

  • 从真实任务、文档和故障中提取专业知识
  • 明确技能边界和不适用范围
  • 编写符合规范的 name 与 description
  • 给出默认流程、关键约束和停止条件
  • 将长资料拆入 references/
  • 将重复的确定性逻辑放入 scripts/

验证阶段

  • 使用 skills-ref 验证格式
  • 准备正向、反向和边界触发样本
  • 比较启用技能与基线结果
  • 为关键输出编写客观断言
  • 检查执行轨迹，而不仅是最终答案
  • 记录质量、耗时和 token 成本

维护阶段

  • 将用户纠正补充到 Gotchas
  • 固定脚本和工具版本
  • 定期删除模型已经能可靠完成的冗余说明
  • 避免为测试集中的具体措辞打补丁
  • 保持主文件精简，并让按需资源的加载条件足够明确

总结

Agent Skills 的价值并不在于多写一份提示词，而在于把真实经验变成一种可发现、可执行、可验证、可迭代的工程资产。

一个成熟技能应同时具备四个特征：

  1. 触发准确：在需要时加载，在近似但无关的请求上保持安静；
  2. 指令有效：提供模型原本缺少的流程、约束和领域事实；
  3. 执行可靠：关键步骤由清晰接口、脚本和验证门禁支撑；
  4. 持续改进：通过基线对比、断言、轨迹和人工反馈迭代。

当技能被当作代码一样设计、评审和测试时，AI Agent 才能从“偶尔做对”逐步走向“稳定完成”。
