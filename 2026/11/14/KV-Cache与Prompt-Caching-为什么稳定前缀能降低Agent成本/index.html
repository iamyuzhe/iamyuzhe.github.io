KV Cache 与 Prompt Caching：为什么稳定前缀能降低 Agent 成本

发表于 2026-11-14 分类于 ai-engineering 阅读次数：
从 Transformer 的 Prefill 与 Decode 出发，解释 KV Cache、跨请求 Prompt Caching 和前缀复用的关系，并给出 Agent 提示词排序、缓存监控与成本判断方法。

长时间运行的 Agent 有一个很容易被忽略的成本来源：每一轮调用模型时，系统提示词、工具定义、项目说明和历史消息都会再次出现在输入中。

如果其中有 2 万个 Token 在 50 轮中保持不变，那么仅这段稳定内容就会累计形成 100 万个输入 Token。Prompt Caching 的价值，就是识别并复用这些相同前缀已经完成的计算。

小红书作者“万有引力 AI”的视频《KV Cache 超轻入门，一篇就够了》围绕这一问题，介绍了 KV Cache、Prompt Caching，以及 Claude Code 如何通过稳定前缀提高缓存复用率。[cite:1] 本文在视频内容基础上，结合 Anthropic、Hugging Face、AWS 与案例原文，进一步区分几个经常混用的概念，并整理成可直接应用到 Agent 系统的工程方法。

一、先区分三个容易混用的概念

KV Cache、Prefix Caching 和 Prompt Caching 有关联，但不是同一个层次的概念。

概念 作用范围 核心作用
KV Cache 一次生成过程内部 复用已经处理过的历史 Token 的 Key、Value
Prefix Caching 多个请求之间 识别相同前缀并复用其计算状态
Prompt Caching API 产品能力 让开发者指定或自动管理可跨请求复用的提示词前缀

最基础的是 KV Cache。跨请求的前缀缓存通常会复用与相同前缀对应的模型状态，而 Prompt Caching 则是模型服务商暴露给开发者的控制和计费接口。

需要注意的是，API 文档通常只保证“相同前缀可被缓存和复用”，并不一定公开服务端如何存储、索引和调度底层张量。因此，“Prompt Caching 就是把 KV 张量按哈希永久保存”适合作为理解模型，不应被当成所有供应商都已公开确认的实现细节。

二、为什么生成模型需要 KV Cache

Decoder-only Transformer 的推理可以分成两个阶段：

Prefill：处理完整输入

Prefill 会一次性读取完整上下文，并在每一层计算注意力所需的中间状态。这个阶段并行度高，通常更受计算能力限制，并直接影响首 Token 延迟，也就是 TTFT（Time to First Token）。[cite:3]

Decode：逐 Token 生成

Decode 每次只产生一个新 Token。每一步都要读取模型权重和此前积累的注意力状态，因此并行度较低，通常更受显存带宽限制。[cite:3]

注意力机制可以简化理解为：

对于已经处理过的历史 Token，它们的 Key 和 Value 不会因为后面出现新 Token 而改变。Hugging Face 的文档说明，KV Cache 会按层保存历史 Token 的 K、V；生成新 Token 时，只计算当前 Token 的 Q、K、V，再把新的 K、V 追加到缓存中。[cite:2]

没有 KV Cache 时，每一步都要重新计算全部历史 Token 的 K、V；使用缓存后，每一步只需为新 Token 计算新的 K、V。其代价是缓存占用会随序列长度线性增长。[cite:2]

三、为什么 Agent 特别适合 Prompt Caching

普通问答可能只调用一次模型，但 Agent 往往采用循环结构：

每一轮请求大致可以拆成两部分。

静态前缀

  • 系统指令和行为规则；
  • 工具名称、说明与参数 Schema；
  • 项目级规则；
  • 长文档、示例或背景资料；
  • 会话期间保持不变的检索结果。

动态后缀

  • 新的用户消息；
  • 模型回复；
  • 工具调用与返回结果；
  • 终端输出；
  • 当前计划和任务状态。

Agent 每走一步，动态后缀都会增长，但前面的系统指令和工具定义往往完全相同。如果模型服务能够复用稳定前缀，就不需要每一轮都重新完成相同的 Prefill。

Anthropic 的 Prompt Caching 文档明确规定，Claude API 按 tools、system、messages 的顺序形成可缓存前缀。后续请求命中相同前缀时，可以降低输入成本和处理延迟。[cite:4]

四、Prompt Caching 怎样计费

截至 2026 年 11 月，Anthropic 的通用定价倍数为：

操作 相对基础输入价格 缓存时长
普通输入 1 倍 不缓存
5 分钟缓存写入 1.25 倍 5 分钟
1 小时缓存写入 2 倍 1 小时
缓存读取 通常为 0.1 倍 命中后刷新 TTL

部分最新模型的缓存读取价格更低。例如 Anthropic 文档显示，Claude Opus 5.5 和 Sonnet 5.5 的缓存读取是基础输入价格的 0.05 倍。具体价格会随模型和时间变化，应以官方定价页为准。[cite:4]

缓存写入比普通输入更贵，因此“开启缓存”并不自动等于省钱。以通用的 0.1 倍读取价格计算：

这意味着 5 分钟缓存通常在第一次复用时就开始节省成本；1 小时缓存则需要更多复用次数才能覆盖额外写入成本。真正的收益取决于：

  • 稳定前缀有多长；
  • 在 TTL 内能复用多少次；
  • 命中的是哪个模型及其缓存费率；
  • 动态后缀占总输入的比例；
  • 是否频繁改变缓存断点之前的内容。

五、92% 命中率和 81% 降本意味着什么

视频引用了 Daily Dose of Data Science 对 Claude Code 的分析：一项跟踪案例处理了约 200 万输入 Token，其中约 184 万 Token 属于可复用前缀，前缀复用率约为 92%。按当时 Claude Sonnet 4.5 的价格估算，无缓存成本约为 6 美元，使用缓存后约为 1.15 美元，下降约 81%。[cite:5]

这个数字来自 LMCache 团队对一次 Claude Code 任务流量的分析。原始实验包含 92 次 LLM 调用，运行约 13 分钟，任务来自 SWE-bench Verified；不同阶段的共享前缀比例从 92% 到接近 98%。[cite:6]

因此，这组数字应该被理解为：

一个高度依赖固定系统提示词、工具定义和循环调用的 Agent，可以获得非常高的前缀复用率。

它不是 Claude Code 所有任务的官方平均值，也不意味着任意 Agent 打开缓存后都能固定节省 81%。任务长度、工具数量、上下文组织和缓存 TTL 都会改变最终结果。

六、稳定前缀应该怎样组织

缓存优化的核心原则可以概括为：

一套实用的上下文顺序如下：

其中前 3 层构成相对稳定的基础，后 2 层持续增长。

不要在稳定前缀中放动态值

以下内容很容易制造不必要的缓存失效：

  • 当前时间戳；
  • 每轮变化的请求 ID；
  • 用户在线状态；
  • 随机排序的工具定义；
  • 不稳定的 JSON 序列化结果；
  • 每轮都重写的状态摘要。

这些值应该放到靠后的动态消息中，而不是写进系统提示词。

会话中不要随意增减工具

工具定义位于 Claude 提示词结构的最前面。增加工具、删除工具，或改变工具 Schema，都会改变后续前缀。[cite:4]

如果工具很多，可以在“缓存稳定性”和“上下文体积”之间做权衡：

  • 高频工具保持固定并提前加载；
  • 低频工具通过稳定的工具集合分组；
  • 不要每轮根据临时判断重新排序；
  • 工具 Schema 的序列化方式保持确定性。

不要原地修改历史前缀

状态变化应尽量以新消息追加，而不是修改已经发送过的系统指令或历史消息。追加操作保留旧前缀，原地修改则会产生新的前缀。

不过，“前面改一个字符，所有缓存都归零”也需要更精确地理解。Anthropic 的显式缓存支持多个断点，并会在每个断点之前向后检查最多 20 个内容块，寻找之前写入过的最长匹配前缀。因此，后部变化不一定使更早的缓存断点失效；真正危险的是修改稳定断点之前的内容。[cite:4]

七、上下文压缩也要保护缓存

当对话接近上下文上限时，常见做法是总结旧消息并开启一个较短的新上下文。如果直接重写整个提示词，可能同时失去已有缓存。

更稳妥的处理方式是：

  1. 保留相同的工具、系统指令和历史前缀；
  2. 在末尾追加“总结当前对话”的请求；
  3. 让总结调用复用已有前缀；
  4. 将总结结果写入下一阶段的新上下文；
  5. 后续会话继续维持新的稳定结构。

子 Agent 也可以降低主上下文膨胀。让探索 Agent 读取大量文件，再只把结构化结论返回主 Agent，可以避免把全部原始工具输出长期留在主 Agent 的动态后缀中。LMCache 对 Claude Code 的跟踪显示，探索、规划和执行阶段采用了不同上下文，并通过摘要在阶段间传递信息。[cite:6]

八、怎样监控缓存是否真的生效

Claude API 的 usage 信息提供三个关键字段：[cite:4]

  • cache_creation_input_tokens：本次写入缓存的 Token；
  • cache_read_input_tokens：本次从缓存读取的 Token；
  • input_tokens：未作为缓存创建或读取处理的输入 Token。

可以同时观察两个指标。

缓存复用率

这个指标关注缓存流量中“读取”相对“新建”的比例。

总输入缓存占比

这个指标更接近“整个输入中有多少内容通过缓存读取”，适合衡量最终成本结构。

监控时不要只看平均值，还应按以下维度拆分：

  • Agent 类型；
  • 模型；
  • 工具集合版本；
  • 会话阶段；
  • 缓存 TTL；
  • 系统提示词版本；
  • 命中和未命中请求的 TTFT；
  • 每个任务的完整成本。

如果发布一次提示词改动后命中率突然下降，通常应先检查工具 Schema、系统提示词、消息顺序和序列化是否发生变化。

九、工程检查清单

在 Agent 上线前，可以逐项检查：

  • 系统提示词是否包含时间、ID 等动态数据；
  • 工具列表与 Schema 是否在会话中保持稳定；
  • JSON 和工具定义的序列化顺序是否确定；
  • 长文档和示例是否放在动态消息之前；
  • 状态变化是否通过追加消息表达；
  • 上下文压缩是否复用旧前缀；
  • 是否根据会话节奏选择 5 分钟或 1 小时 TTL；
  • 是否记录缓存创建、读取和普通输入 Token；
  • 是否按完整任务计算成本，而不是只看单次请求；
  • 是否为不同模型分别评估缓存策略。

十、结论

KV Cache 解决的是自回归生成过程中重复计算历史 Token 的问题；Prefix Caching 将这种复用扩展到具有相同前缀的不同请求；Prompt Caching 则把跨请求复用包装成可控制、可计费、可观测的 API 能力。

对于 Agent，优化重点不只是“打开缓存”，而是设计一个稳定的上下文结构：

当稳定内容足够长、调用轮次足够多时，Prompt Caching 可以同时降低成本和首 Token 延迟。反过来，如果系统提示词、工具 Schema 或前缀顺序持续变化，缓存写入费用反而可能成为额外开销。
