Claude Opus、Sonnet、Haiku 怎么选：从基准测试到分层路由

发表于 2026-11-14 分类于 ai-engineering 阅读次数：
基于 OpenRouter 对 Claude Opus 5.5、Sonnet 5.5、Haiku 5.5 的实测与 Anthropic 官方资料，比较三档模型的能力、成本和适用任务，并给出分层路由与自建评测方法。

Claude 的 Opus、Sonnet 和 Haiku 并不是简单的“高、中、低配”。在真实工程中，模型选型更像一个成本与风险的路由问题：

  • 哪些任务可以交给便宜模型批量处理？
  • 哪些任务需要更稳定的默认模型？
  • 什么情况下值得为 Opus 支付更高成本？

OpenRouter 用同一批编码任务测试了 Claude Opus 5.5、Sonnet 5.5 和 Haiku 5.5。结果很有启发性：三档模型全部通过测试，但单任务成本最多相差约 30 倍。[cite:1]

不过，这不等于“Haiku 已经全面替代 Opus”。短小、定义清晰的测试，无法覆盖长时间、开放式、错误代价高的任务。真正可靠的结论是：默认使用 Sonnet，批量明确任务下沉到 Haiku，复杂高风险任务升级到 Opus，再用自己的评测集校准边界。

一、先看三档模型的定位

截至 2026 年 11 月公开信息，Claude 5.5 家族可以这样理解：

模型 官方定位 更适合的任务 每百万输入 / 输出 Token
Opus 5.5 复杂工作、持续判断和长时间 Agent 任务 架构决策、疑难排障、开放式研究、高风险变更 $4 / $20
Sonnet 5.5 速度、能力和成本的平衡 日常编码、修复 Bug、文档与常规 Agent 工作 $2 / $10
Haiku 5.5 高吞吐、低成本、低延迟 分类、抽取、摘要、查询、子 Agent、批量任务 $0.10 / $0.50

表中 Haiku 的价格适用于不超过 10 万 Token 的提示词；超过 10 万 Token 后，输入与输出价格分别为 $0.50 和 $2.50。Anthropic 还将 Haiku 5.5 定位为目前最快的小模型，特别强调摘要、上下文压缩、数据库查询、分类、在线客服和浏览器操作等场景。[cite:4]

Anthropic 对 Sonnet 5.5 的描述是 Opus 5.5 的低成本、快速补充：它擅长边界清晰的日常任务、Bug 修复以及文档、幻灯片和表格制作；Opus 则用于需要持续判断的复杂开放任务。[cite:2][cite:3]

二、OpenRouter 的测试得出了什么

OpenRouter 做了两组编码测试。第一组要求模型按规格实现 Python 函数，并用隐藏测试验证；第二组让 Claude Code 修复一个包含三个 Bug 的小型发票项目。[cite:1]

1. 25 次隐藏测试全部通过

测试包含 8 个日常任务和 3 个困难任务，例如：

  • 区间合并、LRU 缓存和表达式计算；
  • Cron 下一次运行时间与语义化版本排序；
  • 不使用 re 模块实现正则引擎；
  • 处理 SQL 的三值 NULL 逻辑；
  • 跨时区和夏令时计算空闲日程。

每个模型共执行 25 次，结果都是 25/25 通过。

指标 Opus 5.5 Sonnet 5.5 Haiku 5.5
通过次数 25/25 25/25 25/25
日常任务平均成本 $0.0211 $0.0112 $0.0007
困难任务平均成本 $0.0739 $0.0380 $0.0027
困难任务平均耗时 32.1 秒 25.7 秒 22.6 秒

在这组任务里，模型能力没有拉开差距，成本却明显不同。Haiku 的困难任务成本约为 Opus 的 1/27，而且平均完成时间更短。[cite:1]

2. Claude Code 修复任务也全部通过

发票项目中有三个问题：

  1. 金额计算错误地使用了银行家舍入；
  2. CSV 解析器错误拆分了引号内的逗号；
  3. 汇总逻辑覆盖数量，而不是累加数量。

每个模型各运行三次，九次运行全部修复三个 Bug。

指标 Opus 5.5 Sonnet 5.5 Haiku 5.5
完整修复 3/3 3/3 3/3
单次会话成本中位数 $0.098 $0.062 $0.0052
对话轮数 5 5 6～8
总耗时 24～30 秒 18～25 秒 22～31 秒

Haiku 用了更多轮次，但会话成本仍只有 Sonnet 的约 1/12、Opus 的约 1/19。[cite:1]

这说明单 Token 价格不能直接等同于单任务成本。便宜模型可能需要更多推理 Token、更多轮次或更多重试，所以工程上应该统计完整任务的成功率、总成本和总耗时。

三、为什么不能据此认为 Haiku 等于 Opus

OpenRouter 的测试有两个明确限制：

  • 任务规模小；
  • 输入和验收标准清晰。

这正好是 Haiku 的优势区间。测试没有覆盖大型代码库迁移、跨模块设计、需求不完整的排障、数小时 Agent 运行，或一次错误会造成较大损失的变更。

Anthropic 的官方评测给出了另一面：Opus 5.5 重点面向 Agent 编码、计算机操作和知识工作；Sonnet 5.5 在部分基准和较高 effort 下可以接近 Opus，但 Anthropic 的内部测试和外部试用仍认为 Opus 在复杂、开放、需要持续判断的任务上更强。[cite:2][cite:3]

这两组结果并不矛盾：

所以，不能用一次小型编码测试证明高端模型没有价值，也不能因为 Opus 的能力上限更高，就让所有简单任务都承担 Opus 的成本。

四、实际项目应该怎样选

默认模型：Sonnet

如果只能选一个模型，Sonnet 5.5 是更稳妥的默认值：

  • OpenRouter 的两组编码测试中，它与 Opus 同样全部通过；
  • 每 Token 价格是 Opus 的一半；
  • 官方定位覆盖日常编码、Bug 修复和常规内容生产；
  • 相比 Haiku，它更适合需求存在一定歧义、需要多步推理的主流程。[cite:1][cite:3]

对大多数团队来说，Sonnet 应该先成为基线模型，再根据评测结果向上下两档分流。

高吞吐任务：Haiku

以下任务通常适合优先尝试 Haiku：

  • 文本分类、结构化抽取和路由判断；
  • 摘要、压缩与字段规范化；
  • 大批量、规则清晰的代码修改；
  • 主 Agent 拆出的独立子任务；
  • 可以用测试、Schema 或规则快速验收的工作；
  • 对响应延迟敏感的客服和浏览器操作。

关键不是“任务看起来简单”，而是任务是否边界清晰且结果可验证。如果失败可以被自动测试发现，Haiku 的成本优势更容易安全兑现。

高风险复杂任务：Opus

以下情况更值得升级到 Opus：

  • 需求模糊，需要先澄清目标和约束；
  • 涉及跨模块架构、复杂迁移或疑难根因分析；
  • Agent 需要长时间自主执行并保持上下文；
  • 缺少确定性验收标准，需要依赖判断质量；
  • 错误可能带来生产事故、数据损坏或大量返工。

当错误代价远高于推理成本时，直接使用 Opus 往往比“便宜模型失败后再返工”更经济。

五、比固定选型更有效的是分层路由

六、最终决策要基于自己的评测集

OpenRouter 文章最重要的提醒不是某个模型赢了，而是：他们的任务不是你的任务。[cite:1]

团队可以从历史工作中抽取 20～50 个代表性任务，建立最小评测集：

  1. 覆盖简单、中等、复杂三种难度；
  2. 保留真实输入、工具和上下文长度；
  3. 使用相同提示词分别运行三个模型；
  4. 优先采用单元测试、结构化规则或人工盲评；
  5. 记录成功率、总 Token、总成本、耗时和重试次数；
  6. 对失败任务分析原因，而不只比较平均分。

推荐使用“质量门槛优先”的决策方法：

如果 Haiku 在某类任务中稳定通过，就把这类请求下沉；如果 Sonnet 在复杂任务中频繁需要重试，就将该类任务直接升级到 Opus。模型路由应该是评测结果，而不是品牌偏好。

七、结论

Claude 三档模型的合理分工可以概括为：

  • Sonnet 作为默认模型：覆盖多数日常编码和知识工作；
  • Haiku 负责规模化执行：处理明确、重复、低风险、可验证的任务；
  • Opus 负责能力上限：承担长时间、开放式、高风险且错误昂贵的任务。

OpenRouter 的测试证明了一个重要事实：在边界清晰的任务上，小模型可能以低得多的成本达到相同结果。[cite:1] Anthropic 的官方资料则提醒我们，复杂、开放和持续判断仍是 Opus 的核心价值。[cite:2][cite:3]

因此，最好的问题不是“哪个模型最强”，而是：

在满足当前任务质量门槛的模型中，哪一个总成本最低？
