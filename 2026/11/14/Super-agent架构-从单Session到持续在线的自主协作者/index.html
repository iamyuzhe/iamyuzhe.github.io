Super-agent 架构：从单 Session 到持续在线的自主协作者

发表于 2026-11-14 分类于 ai-engineering 阅读次数：
整理 DeepSeek Harness 团队的 Super-agent 架构探索，分析 Router/Worker 双层架构、事件路由、上下文管理、异步交互、存算分离与 Watchdog 如何共同支撑持续在线的 Agent。

Coding Agent 已经越来越擅长完成单个复杂任务，但当任务数量增加时，新的瓶颈不再是模型会不会写代码，而是人能否持续跟踪多个 Session。

每个 Session 都有自己的上下文、进度和待确认事项。用户需要记住“哪个任务在哪个窗口”“哪条信息已经告诉过哪个 Agent”，还要在任务完成、失败或被新消息打断时手动切换。DeepSeek Harness 团队将这种限制概括为：

单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

为突破单会话模式，团队提出了 Super-agent：一个能够跨会话保持连续上下文、并行推进多个复杂任务、主动响应环境事件，并在长期运行中自动恢复的 Agent 系统。[cite:1]

需要先说明的是，原文讨论的是工程架构探索，并非 DeepSeek Harness 的现有产品功能介绍；配套开源仓库也是研究原型，不是 DeepSeek 正式产品或可直接投入生产的软件。[cite:2]

一、Super-agent 不是更强的单个 Agent

Super-agent 的重点不是换一个更大的模型，也不是让一个 ReAct Loop 同时处理所有工作，而是重新设计 Agent 的运行系统。

它需要同时满足四个特征：

特征 含义
连续 用户可以跨 IM、GitHub、邮件等信道继续同一项工作，不必管理底层 Session
高效 能快速响应交互，并行推进多个复杂任务
主动 持续观察环境事件，在规则允许时主动处理，不必等待逐条指令
持久 始终在线，设备离线或组件异常后仍能恢复

这四个目标之间存在天然冲突。一个 Session 最容易保持上下文连续，却会被串行执行限制吞吐量；为每条消息新建 Session 可以获得并发，却会丢失全局上下文并制造多头回复。

因此，Super-agent 本质上是一个分布式 Agent 系统。它需要调度、路由、隔离、持久化、故障恢复和安全边界，而不只是提示词与工具调用。

二、整体架构：五个模块共同解决四个目标

原文提出五个核心模块：

  1. Router/Worker 双层架构：分离全局协调与具体执行。
  2. 事件驱动：让群聊、代码评审和 CI 等环境变化成为输入。
  3. 面向人的异步多信道交互：后台工作不阻塞前台沟通。
  4. 计算、状态与执行环境分离：实现跨设备、持久在线。
  5. Watchdog：从基础设施故障和任务失控中自动恢复。

单独实现其中一个模块并不能得到 Super-agent。双层架构解决了并发，却不负责持久化；事件驱动带来主动性，也同时扩大了噪音与攻击面；存算分离提高了可恢复性，却需要额外处理凭据和环境隔离。

三、双层架构：Router 管全局，Worker 做任务

Router 层：全局序点

Router 是常驻的全局协调层，承接所有入口的人类交互，并维护跨任务、跨信道的连续性。

它主要负责：

  • 判断新事件是否形成任务；
  • 将任务分派给合适的 Worker；
  • 维护任务之间的高层关联；
  • 汇总 Worker 状态；
  • 统一向用户提问或交付结果。

Router 不直接执行具体任务，甚至可以不具备 Bash 等重型工具。这样可以避免全局节点被耗时工作阻塞，也可以使用速度更快、成本更低的模型。

这与常见 Agent Team 中的 Team Lead 不完全相同。Team Lead 通常深度参与一个复杂任务的拆解和协调；Super-agent 的 Router 只处理不同任务之间的关系，单个任务内部如何规划对它保持透明。

Worker 层：隔离执行

Worker 专注完成一个具体任务，拥有独立上下文和完整工具。由于它直接决定代码质量与任务结果，通常应该配置能力更强的模型。

Worker 之间默认隔离：

  • 不共享长上下文；
  • 不直接向用户回复；
  • 不需要频繁点对点通信；
  • 可以在内部继续创建 Subagent 或 Agent Team。

Worker 的过程信息先汇报给 Router，再由 Router 以统一口径对外沟通。这避免了多个 Agent 同时在群里发送进度、追问和结论。

为什么 Session 应该成为实现细节

现有 Agent 产品经常把 Session 同时当作上下文容器和项目管理单元。用户被迫按照底层 LLM API 的会话边界管理工作。

Super-agent 将产品层任务与底层 Session 解耦。用户看到的是一个持续存在的协作者，系统内部则可以为不同话题创建多个 Worker。一个用户会话不再必须对应一个模型 Session。

四、事件驱动：从等待 Prompt 到观察环境

Super-agent 的主要输入不是用户在聊天框中逐条键入的 Prompt，而是环境持续产生的半结构化事件：

  • IM 群消息；
  • GitHub Issue 与 Pull Request 评论；
  • CI 成功或失败；
  • 邮件与日历提醒；
  • 任务状态变化；
  • 执行环境上线或离线。

原文把这些事件称为 Trigger。事件驱动让 Agent 获得主动性，也带来三个新问题：事件太多、如何找到负责的 Worker，以及应该把多少上下文送给模型。

五、过滤与路由：把 Fast Path 留给程序

两级过滤

真实环境中的绝大多数消息不需要 Agent 介入。如果所有事件都调用大模型判断，成本和延迟都会迅速失控。

Super-agent 使用 Fast Path / Slow Path 两级过滤：

层级 处理方式 适用判断
程序层 Fast Path 确定性代码 来源、群组、用户白名单、机器人消息、明确忽略规则
语义层 Slow Path LLM 判断 是否值得介入、是否形成任务、应该采取什么行动

稳定、高频且确定的判断应固化为代码；只有需要语义理解的候选事件才进入模型。

这条原则很重要：Agent 系统不应该把所有决策都交给 Agent。确定性规则更便宜、更快，也更容易审计。

Thread 订阅与直通

同一个 PR、IM 话题或邮件串中的连续事件可以组成一个 Thread。

Router 只负责 Thread 的第一个事件：

订阅后的事件走 Fast Path，程序直接投递给 Worker，不再经过 Router 的模型推理。未被订阅的新事件才走 Slow Path，由 Router 决定归属。

Thread 与 Worker 可以是多对多关系。一个 Worker 可以订阅多个相关 Thread，一个 Thread 也可以被多个 Worker 观察。多个 Worker 在同一 PR 发生交集时，会收到相同事件，从而发现冲突。

六、上下文管理：把窗口当作 Cache

事件系统会持续产生上下文，但模型窗口始终有限。全部注入会稀释注意力，只给 ID 又会导致模型频繁调用工具。

原文借用缓存和局部性思想，将上下文管理概括为 Inline & Spill：

  • Inline：把近期高概率使用的信息直接放进当前上下文；
  • Spill：把低频或过长内容留在窗口之外，只保留摘要、ID 和读取入口。

一个实用的渐进策略是：

  1. 先注入当前对象的 ID 和摘要；
  2. Inline 紧密关联对象的 ID；
  3. 加入时间和空间相邻内容，例如消息上下文或相邻评审评论；
  4. 对长内容设置上限，超出部分 Spill；
  5. 模型需要时再通过工具读取完整内容。

在 Trigger、Thread 和 Worker Session 之间保留引用关系后，这些对象会形成一张引用图。模型可以从当前消息出发，按需追踪到所在 Thread、相关 Worker，再找到另一个代码评审 Thread。原文将这种多跳按需检索称为 Chain of Recall。[cite:1]

七、提前行动：用后台算力换人类等待时间

Super-agent 还引入了类似投机执行的策略。

当环境信号表明某项工作可能有价值时，Agent 可以先在后台尝试：

  • 收到会议邀请后检查日程冲突并准备回复；
  • 群里出现缺陷反馈时静默复现；
  • 讨论修改方案时提前检查代码影响；
  • CI 失败后定位原因并准备修复。

只有确认问题存在并找到有价值的结果后，Agent 才通知用户；没有价值的尝试直接丢弃。

投机执行的目标不是让 Agent 更活跃，而是用可控的后台算力减少人类等待和沟通成本。它必须受明确规则、资源预算和权限边界约束，否则主动性很容易变成噪音或风险。

八、异步 ReAct Loop：后台任务不能阻塞对话

这样，前台交互与后台执行实现全双工。用户可以补充条件、改变方向或停止任务，而不必等待当前工具调用结束。

原文说明，这一异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。[cite:1] DeepSeek Harness 官方将模型、工具、Session、沙箱、存储、循环和 UI 都设计为可替换插件，并通过追加式 Session 日志记录模型看到的内容和工具轨迹，为这种组合式架构提供了基础。[cite:3]

九、多信道交互：输出带宽要匹配工作场景

终端、群聊、Pull Request 和邮件的交互习惯不同，不能使用同一种输出策略。

信道 推荐输出
IM 群聊 低打扰，只在需要决策或有可用结果时回复
GitHub PR / Issue 结构化说明背景、改动、风险和验证结果
邮件 完整但克制的异步交付
文档 可复用的长期信息与决策记录

Worker 内部可以保留详细推理和工具轨迹，但不应该把这些内容原样倾倒到群聊。Router 需要根据目标信道压缩、组织并选择输出时机。

十、计算、状态与执行环境分离

本地 Agent 往往把三件事绑定在一台机器上：

  1. 推进 Agent Loop 的计算；
  2. 需要持久化的 Session 状态；
  3. 代码、依赖、凭据和工具所在的执行环境。

设备休眠后 Agent 就停止，容器失败后状态可能丢失，也难以跨设备访问真实工作环境。

Super-agent 分两步解耦：

第一步：计算与状态分离

Agent Loop 运行在无状态计算容器中，Session 等持久状态存入数据库。计算容器可以扩缩、重启或替换，新的实例从持久化事件中恢复进度。

第二步：计算与执行环境分离

Agent Loop 常驻云端，真实开发机或个人设备保留在原地，只运行一个轻量 daemon。云端 Agent 按需调用端侧环境中的工具，而不必复制未提交修改、内网依赖、硬件工具链和本地配置。

Anthropic 在 Managed Agents 中采用了相似的“脑手分离”设计：将 Harness、Session 日志和 Sandbox 拆成独立接口，使每个组件都可以独立失败和替换；Session 状态位于 Harness 外部，执行环境则像普通工具一样按需连接。[cite:4]

两者的侧重点不同：Anthropic 主要讨论托管沙箱和客户 VPC，Super-agent 文章还特别关注间歇在线的个人机器和 BYOM（Bring Your Own Machine）。

十一、Watchdog：不仅看进程，还要看任务是否前进

长期运行系统不能只依赖主系统自救，需要外部 Control Loop。

传统健康检查只能判断进程是否存活，却无法识别 Agent 是否：

  • 陷入无效循环；
  • 长时间没有实质进展；
  • 偏离原始目标；
  • 因外部偶发故障反复失败；
  • 给出形式完成但实际未交付的结论。

因此，原文在主系统外设置独立的 Watchdog Session，由定时消息驱动。它既检查接口错误、状态恢复失败等基础设施问题，也由模型判断 Worker 的任务进展和方向。

Watchdog 本身拥有工具能力，维护者可以用自然语言查询故障原因、调整 Trigger 规则或修改提示词。但它必须独立于被监控系统，否则主系统发生故障时，监控也会一起失效。

十二、初步实验说明了什么

原文使用合成的群聊与 GitHub CI 消息流进行了初步实验。每次约 300 条消息，其中约 20 条是工作请求，其余是闲聊、跟进、停止指令和 CI 消息；每种方案重复运行 5 次。编码任务由只消耗时间的工具替代，因此实验衡量的是调度与协作，而不是编码能力。[cite:1]

双层架构降低了完成时间长尾

Super-agent 的任务完成时间：

  • p50：12.4 分钟；
  • p95：15.7 分钟。

中性提示下的单 Session 从未调用 Subagent，任务持续被新消息打断，p95 达到 29.5 分钟。即使通过提示词要求优先委派，模型仍可能临场决定亲自执行“小任务”，形成不稳定长尾。

这个结果支持一个工程判断：关键调度约束应该落实在系统结构中，而不是只依赖模型遵守提示词。

直通机制主要节省 Router 开销

移除 Thread 直通后，任务完成时间与完整方案基本一致，但 Router 决策次数增加约 30%，总读缓存 token 从 2323 万增加到 3177 万，增幅约 37%。[cite:1]

直通没有直接改善实验中的完成速度，却显著减少了全局 Router 的推理负担。

Router 批处理吸收突发事件

当待决策 Trigger 的到达速率从每分钟约 1 条提升到约 40 条时：

指标 低负载 高负载
平均 batch 大小 1.0 2.8
单次请求耗时 2.5 秒 3.9 秒
单个决定分摊推理时间 6.4 秒 1.6 秒

积压事件在下一轮合并进入模型，Prefill 可以并行处理长输入，因此单次请求耗时的增长慢于 batch 大小。

这些数据只能视为架构方向的初步证据。实验使用合成负载、简化执行工具且样本较少，不能直接推导生产环境的吞吐上限或成本收益。

十三、落地时最容易忽略的边界

原型不等于完整实现

开源的 dsh-superagent-prototype 是面向单个 GitHub 仓库的主动式 Coding Agent，可监听 GitHub，并可选接入飞书；它将工作拆成独立 Session 和目录，再回到原始对话交付结果。[cite:2]

仓库明确说明：

  • 它是研究代码，不是生产级软件；
  • 发布版本与内部实现并不完全相同；
  • 文章中的部分设计仍是未来方向；
  • 使用前必须自行审查和适配。

主动性会扩大安全风险

事件驱动意味着 Agent 会持续接触不可信消息、评论和文档。云端 Agent 又可能连接包含私有代码、敏感数据和凭据的端侧设备。

一旦提示词注入或服务端入侵控制 Agent Loop，所有连接设备都可能暴露。仅靠“限制 Prompt”无法解决这一问题，还需要：

  • 最小权限与明确授权范围；
  • 将凭据保留在模型无法读取的位置；
  • 对工具和资源进行策略代理；
  • 隔离不同组织和用户的上下文；
  • 对主动行动设置审批、预算和审计；
  • 允许随时中止并撤销访问。

Anthropic 的架构同样强调凭据不能出现在运行模型生成代码的 Sandbox 中，而应通过外部 Vault、代理和资源绑定完成授权。[cite:4]

长期记忆仍然没有通用答案

引用图与链式召回适合近期任务，但跨月甚至更长周期的记忆仍然困难。如何决定压缩什么、保留什么、何时遗忘，以及如何在不同权限边界间共享信息，仍是开放问题。

十四、适合团队采用的渐进路线

不必一次搭建完整 Super-agent。更稳妥的落地顺序是：

阶段一：把任务与 Session 解耦

建立独立任务 ID、状态和交付记录，让 Session 可以重建，而不是把所有进度只留在聊天历史中。

阶段二：引入 Router/Worker 边界

Router 只分派和沟通，Worker 隔离执行。先限制并发数，并为每个 Worker 分配独立目录或 worktree。

阶段三：接入单一事件源

从 GitHub Issue 或 PR 开始。先做白名单和明确请求，再逐步增加语义判断，不要一开始监听所有群消息。

阶段四：建立 Thread 订阅

让后续评论直达已有 Worker，减少 Router 重复判断。保留重新路由和取消订阅能力。

阶段五：异步执行与持久状态

将长任务改为后台运行，执行结果以事件回注；把 Session 日志、任务状态和审计信息保存到外部存储。

阶段六：增加 Watchdog 与安全门禁

同时监控基础设施与任务进展。对写操作、跨设备访问、外部消息和凭据使用建立清晰的授权策略。

总结

Super-agent 的关键变化，是把 Agent 从“一个对话窗口里的循环”重新定义为“一个持续运行的系统”。

Router/Worker 双层架构解决连续性与并发的冲突，事件过滤和 Thread 订阅控制主动响应的成本，Inline & Spill 管理有限上下文，异步 ReAct Loop 将交互与后台执行解耦，计算、状态和环境分离提供持久性，Watchdog 则补上长期运行所需的外部控制回路。

这套设计并没有发明全新的计算机科学概念。它的价值恰恰在于把 Fast/Slow Path、缓存、局部性、投机执行、存算分离和 Control Loop 等成熟系统思想，重新应用到 Agent 架构中。

模型越能独立完成任务，人的工作就越应该从管理 Session 和盯执行过程，上移到定义目标、设置边界、处理例外与验收结果。
