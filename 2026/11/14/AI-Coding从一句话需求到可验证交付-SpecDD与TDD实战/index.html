AI Coding 从一句话需求到可验证交付：SpecDD 与 TDD 实战

发表于 2026-11-14 分类于 software-engineering 阅读次数：
根据知乎知学堂课程的完整实战，整理如何把模糊的一句话需求转成可持续管理的 Spec，再以测试约束 Coding Agent，形成从定义、实现到验收的闭环。

Coding Agent 已经可以根据一句话生成一个应用，但“一句话能生成”不等于“一句话足以交付”。

贪吃蛇、俄罗斯方块这类需求之所以看起来简单，不是因为模型真正解决了需求分析，而是这些名称本身就是高密度的通识表达：规则、交互和失败条件早已形成广泛共识。真实业务中的“直播间评论助手”“订单管理系统”或“运营分析工具”没有这种幸运，同一个名称背后可能对应完全不同的产品。

这篇文章整理自知乎知学堂课程 《大厂优秀工程师使用 AI Coding 的最新方法与经验》。课程用一个“抖音直播间评论助手”的现场开发，完整演示了如何通过 SpecDD 和 TDD，把模糊目标变成可审查、可执行、可验证的工程约束。[cite:1]

一、AI Coding 的瓶颈已经从生成转向定义

课程先让学员解释“直播间评论助手”是什么，答案很快分叉：

  • 抓取评论并转成语音；
  • 用 AI 自动回复；
  • 统计评论量与情绪；
  • 对评论分类；
  • 识别违规内容；
  • 管理用户和拉黑账号。

这些答案都合理，却不属于同一个产品。问题不在 Coding Agent 能不能写代码，而在于它应该写哪一种代码。

因此，课程把初始需求改写成：

用户提供一个抖音直播间的 Web 地址，系统监听直播期间的观众评论；监听一段时间后，用户可以让 AI 助理根据已经收集的评论记录回答问题。

这段描述仍不是完整 Spec，但已经回答了五个关键问题：

维度 直播间评论助手示例
场景 抖音直播间正在产生观众评论
输入 一个可访问的直播间 Web 地址
功能 监听评论，并提供基于评论记录的 AI 问答
输出 实时评论流和问题答案
限制 先只支持抖音 Web 直播间

这也是 AI Coding 时代最重要的能力迁移：编码成本下降后，定义问题、缩小范围和判断价值反而成为瓶颈。

二、Plan 不等于 Spec

大多数 Coding Agent 都有 Plan 模式。它会阅读需求、追问缺失信息、选择技术方案，并生成一份执行计划。

但课程强调：

没有保存进项目、不能持续更新的 Plan，还不能称为 Spec。

Plan 是一次交互过程中的临时产物；Spec 则是项目资产。它必须进入仓库，接受版本管理，并在开发过程中持续修订。

Spec 同时服务两个受众：

  1. 给 Agent 使用：约束后续实现，减少上下文丢失和自由发散。
  2. 给人使用：理解产品定义、技术决策、执行进度和验收标准。

Anthropic 的 Claude Code 最佳实践也建议：先给 Agent 足够的上下文，复杂任务先使用 Plan 模式，明确什么结果才算正确，并为 Agent 提供可以自行运行的验证方式。[cite:2]

所以 SpecDD，也就是 Specification-Driven Development，不是“写一篇很长的文档”，而是让稳定、可审查的规格持续驱动开发。

三、审查长 Plan 时，先找三件事

Agent 生成的计划往往很长。课程没有要求逐字阅读，而是按角色和任务阶段提取重点。

对于一个全新功能，首先检查：

  1. 功能定义是否正确
  2. 还有哪些问题没有澄清
  3. 达到什么条件才算完成

非技术人员应先判断核心行为是否与业务目标一致。资深工程师再继续审查技术栈、系统边界、数据流、安全风险和实现路线。

对于旧功能升级或 Bug 修复，还要增加：

  • 问题定义是否准确；
  • 根因和证据是否充分；
  • 修改会影响哪些既有行为；
  • 技术路线是否只是绕过问题；
  • 哪些回归测试必须保留。

重点不是读完 Agent 输出的每一个字，而是在正确阶段审查正确的信息。

四、Spec 负责事前正确，Test 负责事后正确

只有 Spec，仍然无法知道最终实现是否符合约定；只做一次人工验收，也无法保证下一次修改不会破坏原有功能。

课程用一句话概括 TDD 的底层逻辑：

严格 TDD 要求先写测试，再写实现，并经历 Red-Green-Refactor 循环。课程并不要求所有项目机械遵循顺序，而是区分了两种方式：

  • 严格 TDD：测试先于实现，失败测试直接驱动开发；
  • 宽松 TDD：不强制先后顺序，但必须持续沉淀测试，并用测试约束当前和后续实现。

在 AI Coding 场景中，真正重要的是“预期必须可执行”，而不是流程名称。

DORA 对 AI 辅助开发的研究指出，代码生成速度提升并不会自动带来交付质量提升；当验证能力跟不上时，节省的生成时间会转移为评审、返工和稳定性成本。[cite:3] 因此测试不是 AI 生成后的附加步骤，而是 Agent 工作流的一部分。

五、测试优先级不是越多越好

课程把测试设计分成三个优先级：

以直播间评论助手为例，第一层必须验证：

  • 可以输入任意抖音直播间地址；
  • 可以开始和停止监听；
  • 页面能够展示实时评论；
  • AI 助理只基于已收集评论回答问题。

第二层验证主要流程：

  • 没有评论时给出明确状态；
  • 模型 API 未配置时正确报错；
  • 网络超时后可以恢复；
  • 停止监听后不会继续写入数据。

第三层再覆盖边界情况：

  • 地址无效或直播已经结束；
  • 评论量突然激增；
  • 评论中含有异常字符；
  • 用户的问题超出已有评论范围。

测试不是为了制造一个看起来很完整的数字，而是先锁住最不能变化的业务价值。

六、实现和测试可以并行，但写入边界必须分离

现场演示中，Agent 根据同一份 Spec 同时推进两件事：

这两个任务共享只读输入，却写入不同对象，因此可以并行。判断能否并行的关键不是任务名称，而是：

  1. 两个任务是否会修改同一批文件；
  2. 一个任务是否依赖另一个任务尚未产生的结果；
  3. 是否可能反向修改共同的上游约束；
  4. 失败后能否独立回滚和重试。

Anthropic 对长时间运行 Agent 的实践也建议，将大型任务拆成清晰的小批次，记录未完成事项，让不同 Agent 在隔离环境中工作，并在每个阶段保留可恢复的 Git 状态。[cite:4]

并行的价值不是同时打开更多会话，而是在不增加冲突的前提下缩短反馈周期。

七、不要让 Agent 靠对话上下文记住任务

课程在问答环节分享了一个很实用的做法：复杂任务不一定要机械套用某个 TDD Skill，但不要让 Agent 只靠上下文记忆目标。

更稳妥的方式是在仓库中维护行动记录：

Agent 每完成一项就更新状态，只有完成条件全部满足才允许结束任务。

这与 Anthropic 的长任务 Harness 方法一致：使用结构化功能清单、进度文件、自动测试和 Git 历史，让新会话可以从明确状态继续，而不是重新猜测上一轮做了什么。[cite:4]

八、现场演示最有价值的部分，是它没有一次成功

实战最终做出了可用页面：

  • 能监听真实直播间评论；
  • 评论流会实时刷新；
  • AI 可以概括出镜人物、主要内容、互动和人气。

但当讲师追问“哪一段时间表现更出色”时，系统没有给出可靠答案，因为采集结果缺少足够的时间信息。

这次失败说明了三个问题：

  1. 页面能运行，不代表业务目标已经达成；
  2. 测试通过，不代表测试覆盖了真正重要的语义；
  3. 只有在真实场景中追问，才会暴露 Spec 遗漏。

正确处理方式不是临时修改 Prompt，而是把发现写回工程闭环：

GitHub 将这种工作方式概括为 agentic engineering：工程师的职责从逐行生产代码，转向定义任务、提供上下文、建立反馈回路、审查结果和管理多个执行单元。[cite:5]

九、一套可以直接使用的工作流

结合课程实战与官方实践，可以把一次 AI Coding 任务整理成九步：

1. 写清原始目标

说明用户、场景、输入、核心行为、输出和限制。暂时无法确认的内容明确标为问题，不要让 Agent 自行补齐业务事实。

2. 用 Plan 模式澄清

让 Agent 阅读代码和需求，提出问题、识别风险并给出实现路线。此阶段只规划，不修改代码。

3. 将结论保存为 Spec

把功能定义、非目标、技术约束和验收条件写入仓库，纳入 Git 管理。

4. 人工审查关键点

新功能先看功能定义、问题清单和达成标准；改造任务再看根因、影响面和回归风险。

5. 从 Spec 派生测试

先覆盖核心功能，再覆盖主要流程，最后补边界情况。能自动化的验收条件尽量变成可执行测试。

6. 拆分独立任务

按文件、模块或职责划分写入边界。只有互不冲突的任务才并行执行，必要时使用独立 worktree。

7. 让 Agent 自己验证

提供测试命令、类型检查、Lint、构建命令、浏览器或运行日志，让 Agent 能看到动作结果。

8. 做真实端到端验收

不要只读最终总结。亲自走一遍核心用户路径，并用真实数据提出业务问题。

9. 把失败写回系统

将遗漏更新到 Spec，将故障变成测试，将关键决策写入项目文档。下一次任务应从更高的信息基线开始。

总结

AI Coding 的核心能力，不是把 Prompt 写得更花哨，而是建立一套稳定的约束和反馈系统。

Spec 负责把模糊目标变成可管理的预期，测试负责把预期变成可执行的判断，真实验收负责发现文档和测试都没有覆盖的问题。三者共同形成闭环：

当生成代码不再稀缺，工程质量取决于能否正确回答三个问题：我们究竟要做什么，怎样证明它做对了，以及下一次修改时如何确保它仍然正确。
