AI Coding 时代，研发团队如何重新分工与协作

发表于 2026-11-02 分类于 software-engineering 阅读次数：
根据陈博士的课程，整理 AI Coding 对研发岗位、协作边界和工程流程的影响，并给出一套从需求、Spec、开发到验证的可执行协作方法。

AI Coding 带来的变化，不只是程序员写代码更快。

当一个人可以借助 Coding Agent 完成过去需要多人配合的工作时，生产力的变化会继续传导到团队结构、岗位边界和协作方式。产品经理、前端、后端、测试、运维和架构师不会在一夜之间消失，但他们之间“传递什么、共同决定什么、由谁验证结果”都需要重新设计。

这篇文章整理自陈博士的课程 《AI Coding 中的团队重新分工与新协作模式》。课程从一人公司和小规模团队讲起，重点讨论了自然语言交互、岗位能力融合、Spec 驱动协作、Agent 反馈循环，以及多人开发中的冲突控制。[cite:1]

一、真正改变的不是工具，而是生产关系

课程先提出了一个背景：AI 降低了软件生产的单位成本，使一人公司和小规模团队变得更可行。

但“一个人能写更多代码”并不是结论。更重要的问题是：

  • 原来十个人完成的工作，现在需要几个人？
  • 原有前端组、后端组、测试组和运维组是否还要保持相同规模？
  • 研发负责人应该继续按专业分组管理，还是围绕产品和系统边界重新组织？
  • 节省出来的时间应该用于继续增加代码量，还是理解业务、设计系统和验证结果？

DORA 2025 年的研究将 AI 定义为组织能力的“放大器”：它既会放大清晰的流程、良好的平台和稳定的质量体系，也会放大混乱的需求、薄弱的测试和模糊的责任边界。最大的收益并不单独来自工具，而来自对整个组织系统的改造。[cite:2]

因此，AI Coding 的落地顺序不应该是“先买工具，再按人头计算节省了多少成本”，而应该是：

二、从 CLI、GUI 到 LLM：人与软件的接口变了

课程用三代交互方式解释了这次变化。

CLI：人必须学会机器的表达

命令行界面要求使用者记住精确指令：

它高效、确定，但表达方式不自然。使用者必须知道机器接受什么命令，才能驱动系统。

GUI：设计师把有限行为包装成界面

图形界面将文件、数据和代码层包装成按钮、表单和页面。设计师预先猜测普通用户要完成哪些任务，再将这些有限行为呈现在界面中。

GUI 解决了易用性问题，但没有消除边界：没有出现在界面上的行为，用户通常无法完成。

LLM：软件开始理解不完整的自然语言

大模型让用户可以直接描述目标，而不是先学习按钮和命令。问题在于，自然语言天然包含歧义、缺失信息和隐含条件。

例如，“做一个下单功能”至少还缺少：

  • 谁可以下单，入口在哪里；
  • 页面需要展示哪些信息；
  • 哪些字段必填，哪些字段可选；
  • 库存、价格、优惠和支付如何联动；
  • 超时、重复提交和失败重试如何处理；
  • 订单与支付服务之间如何保证一致性。

LLM 降低了表达门槛，却没有消灭需求分析。恰恰相反，它让“把模糊目标变成可验证约束”的能力更加重要。

三、岗位不会简单消失，而是向上下游延伸

课程认为，AI 首先打破的是专业岗位之间最坚固的墙。

过去，产品负责需求，前端负责交互，后端负责业务逻辑和数据，测试负责验收，运维负责运行。AI Coding 让每个角色都能跨过原来的一部分边界，于是团队出现“左右移动”：

角色 过去的主要交付 AI Coding 时代需要增加的能力
产品经理 原型、需求文档、排期 写清 Spec、制作可运行 Demo、验证技术方案
前端工程师 页面与交互 理解接口、数据模型和端到端业务流程
后端工程师 业务逻辑与数据处理 理解用户路径、可观测性和运行约束
测试工程师 用例与验收 提前定义可测试的验收条件，构建自动验证
运维 / SRE 部署、容量与故障处理 在设计阶段提供环境、安全、恢复和运行约束
架构 / 技术负责人 技术选型与系统设计 管理 Spec、边界、质量门禁和持续反馈

这里的重点不是要求每个人都成为“全栈工程师”，而是让每个人都能理解相邻环节，并能检查自己的输出是否真的进入了完整系统。

GitHub 对四个国家 2,000 名企业软件从业者的调查显示，受访者通常把 AI 节省出的时间用于系统设计、协作和学习；在美国和德国，47% 的受访者表示会将额外时间投入协作与系统设计。[cite:3] 这说明高价值工作正在从单纯的代码生产，转向问题定义、系统判断和跨角色协作。

四、产品经理的交付物要从“文档”升级为“可验证设计”

传统需求经常在岗位之间逐级传递：

每次传递都会损失上下文。到了开发环节，工程师可能只拿到一份不完整的说明，然后说：“需求不清晰，文档不全面，做不了。”

AI Coding 时代，产品经理的核心能力不应只是写文档，而是完成三件事：

  1. 把目标写成 Spec
    明确业务场景、用户路径、状态变化、边界条件和验收标准。

  2. 用 Demo 证明设计
    借助 AI 快速做出局部可运行的 MVP，让用户、业务方和研发围绕同一个对象讨论。

  3. 把技术约束纳入方案
    理解数据从哪里来、接口如何交互、哪些行为必须确定、哪些部分可以由 AI 判断。

Demo 不是为了替代正式研发，而是为了更早暴露错误。一个可以操作的粗糙原型，往往比几十页描述更容易发现流程遗漏和理解偏差。

五、开发者的价值从“写出代码”转向“定义与验证系统”

当 Agent 能够生成前端、后端、测试和脚本时，工程师最稀缺的能力不再是把明确指令翻译成代码，而是：

  • 判断需求是否完整；
  • 设计模块边界和数据契约；
  • 选择技术方案；
  • 识别安全、性能和一致性风险；
  • 构建自动测试与运行反馈；
  • 判断产出是否真的解决了业务问题。

GitHub 与 Accenture 的企业研究观察到，使用 Copilot 的参与者在 Pull Request、合并率和成功构建等指标上有所改善，但这项研究依然依赖代码评审和 CI 测试来判断产出质量。[cite:4] AI 提高生成速度后，评审、测试和运行反馈不是可以省略的成本，而是防止错误被更快放大的必要机制。

课程用“无效成功”概括了一个常见风险：

AI 看起来帮人把事情做成了，但人在过程中没有积累对系统的理解，结果也没有经过足够验证。

例如，Agent 修复了页面加载问题，却引入了不合适的鉴权方式；解决了局部数据库问题，却破坏了连接管理；让功能运行起来，却没有解释隐藏规则和异常路径。结果表面可用，系统知识却没有沉淀，下一次修改仍然只能重新猜测。

六、不要只检查最终答案，要建立执行与反馈循环

课程给出了一种更接近工程实践的循环：

人不能只在最后问“结果对不对”，还需要在关键节点注入业务背景、隐藏规则和异常情况。

课程专门分析了一个看起来很巧妙、实际却容易失效的做法：

如果人完全退出，两个 Agent 只使用同一批初始信息，这个循环就像“左脚踩右脚”。无论迭代多少次，系统都不会凭空获得新的业务背景；一旦初始规则或标准答案存在偏差，循环只会反复强化同一个方向。

问题不在于角色分离本身，而在于反馈是否带来了新的有效信息。评估 Agent 必须连接真实的 Spec、自动测试、运行日志、用户反馈和人工判断。人仍然需要处理目标、边界和冲突，并在观察到异常时补充隐藏规则。

Anthropic 在长时间运行 Coding Agent 的实践中也发现，Agent 容易一次做得太多、过早宣布完成，或在没有端到端验证时将功能标记为成功。其改进方法包括维护结构化功能清单、每次只推进一个功能、记录进度、保留 Git 历史，并在标记完成前进行真实的端到端测试。[cite:5]

七、AI 不会一次性替换整个系统

课程提出了一个重要判断：传统系统仍然会长期存在，AI 会逐步进入系统并成为其中一部分。

可以把演进理解为：

订单金额、库存扣减、权限校验和账务一致性等底层行为仍需要确定性。AI 更适合处理自然语言、非结构化信息、方案探索和需要上下文判断的部分。

因此，正确方向不是用 AI 覆盖所有代码，而是明确：

  • 哪些环节必须确定；
  • 哪些环节可以概率化；
  • AI 可以访问哪些数据与工具；
  • 失败时如何降级；
  • 谁对最终结果负责。

八、多人协作应该围绕边界和 Spec 展开

AI 提高了单人的输出速度，也会增加多人并行时的冲突。如果每个人都让 Agent 同时修改共享代码，团队只会更快地产生合并冲突和重复方案。

课程给出了四条原则：

  1. 先理清系统结构，再分工
    以清晰的模块、接口和数据边界实现解耦。

  2. 涉及多个模块时，先讨论再开发
    订单与支付、账号与权限等跨域变更，需要先确认契约。

  3. 把结论写入 Spec
    口头共识会消失，文档化的接口、状态和验收条件才能成为 Agent 与人的共同上下文。

  4. 有争议时使用分支做实验
    不要在主分支上争论抽象方案。分别实现、测试和比较，再将结论合并回主线。

这里的 Spec 不是一份静态长文档，而是一组可以被执行和验证的约束：

九、一套可执行的 AI Coding 协作流程

结合课程内容，可以将一次功能开发整理为七个步骤。

1. 先定义问题

写清用户是谁、问题是否真实、业务为什么愿意为它投入，以及什么结果才算成功。

2. 制作最小 Demo

用 AI 快速做出可操作原型，验证用户路径和核心假设。Demo 只需要覆盖关键场景，不追求完整工程质量。

3. 把共识转成 Spec

记录范围、状态、数据、接口、异常路径和验收条件。产品、研发、测试和运维共同补充约束。

4. 按系统边界拆分任务

让不同的人或 Agent 负责相互独立的模块。跨模块依赖先确定契约，不在实现过程中临时猜测。

5. 生成与评估分离

实现者负责产出代码，评估者依据 Spec、静态检查、测试和安全规则提出问题。

6. 做端到端验证

不要只看单元测试或最终页面。需要验证真实用户路径、数据变化、失败恢复和运行指标。

7. 沉淀组织知识

将架构决策、失败原因、测试方法和运行约束写入仓库，让下一次人或 Agent 不必重新推理。

十、管理者应该优化系统，而不是只压缩人数

AI 能力提升后，管理者很容易直接提出：“原来十个人，现在几个人就够了？”

课程提醒，单纯减少人数可能同时删除系统所需的隐性知识。更稳妥的做法是先观察：

  • 哪些工作只是重复翻译和手工搬运；
  • 哪些角色承担了关键判断与风险控制；
  • 哪些协作可以被 Spec、自动测试和平台能力替代；
  • 哪些知识仍然只存在于个人经验中；
  • 哪些模块适合由更小的端到端团队负责。

团队重构的目标不是让所有人都变成“会提示词的全栈开发”，而是减少低效交接，让更多人具备端到端判断能力。

总结

AI Coding 最深刻的影响，不是代码生成，而是重新定义人与软件、人与岗位、岗位与系统之间的接口。

产品经理需要从描述需求走向证明设计，开发者需要从实现任务走向定义和验证系统，测试与运维需要更早进入约束设计，技术负责人则要维护边界、Spec、质量门禁和反馈循环。

小团队确实可能完成过去大团队才能完成的工作，但前提不是每个人都做所有事情，而是让分工建立在清晰的系统边界上，让协作建立在可执行的 Spec 上，让 AI 的每一次产出都进入验证和知识沉淀循环。

AI 可以提高成功速度。只有组织同时保留判断、验证和学习能力，这种成功才不是“无效成功”。
