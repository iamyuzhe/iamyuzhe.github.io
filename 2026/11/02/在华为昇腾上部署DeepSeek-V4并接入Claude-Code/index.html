在华为昇腾上部署 DeepSeek V4，并接入本地 Claude Code

发表于 2026-11-02 分类于 ai-engineering 阅读次数：
根据陈博士的课程，整理 DeepSeek V4 的关键架构、华为昇腾上的 vLLM-Ascend 部署流程、性能验证方法，以及将本地模型接入 Claude Code 的完整思路。

在本地使用 Claude Code，通常只需要安装客户端并配置云端 API。但在企业环境中，代码、文档和工具调用数据可能不能离开内网，模型成本、并发和可用性也需要由团队自己控制。

这时，问题就从“怎样调用一个模型”变成了：

这篇文章整理自陈博士的课程 《在华为昇腾算力平台上部署 DeepSeek 模型，并连通本地 Claude Code》。课程先解释 DeepSeek V4 的 Agent、注意力和缓存设计，再通过 vLLM-Ascend 完成部署与压测，最后把服务接入 Claude Code。[cite:1]

一、为什么选择 DeepSeek V4 做 Coding Agent

DeepSeek V4 不只是一次通用能力升级。官方说明中专门提到，它针对 Claude Code、OpenClaw、OpenCode 和 CodeBuddy 等 Agent 产品进行了适配，在代码与文档生成任务上提升明显。[cite:2]

这对 Coding Agent 很重要，因为 Agent 的请求与普通问答不同：

  • 系统提示词和工具定义很长；
  • 需要读取大量代码和历史对话；
  • 一次任务可能发生多轮工具调用；
  • 模型既要规划，也要稳定地产生结构化参数；
  • 修改代码前后需要保留完整上下文。

DeepSeek V4-Pro 与 V4-Flash 都支持百万上下文、思考模式和工具调用。复杂 Agent 任务还可以通过 reasoning_effort 控制推理强度。[cite:2][cite:3]

从选型角度看：

模型 更适合的场景
DeepSeek V4-Pro 高难度编码、复杂规划、长链路 Agent 任务
DeepSeek V4-Flash 日常开发、低延迟交互、成本敏感型任务

私有部署并不意味着一定要选择参数最大的模型。团队更应该根据硬件容量、并发、首 Token 延迟和任务难度选择版本。

二、长上下文为什么首先是一个显存问题

课程用 Attention 和 KV Cache 的计算过程解释了长上下文的成本。

自回归生成每个新 Token 时，模型都需要参考前面的上下文。如果重复计算所有历史 Token，代价会非常高。因此推理引擎会保存历史 Token 的 Key 和 Value，这就是 KV Cache。

因此，“模型权重能放进显存”并不代表服务可以稳定运行。上下文从 32K 扩大到 1M 后，KV Cache 往往成为容量规划的核心变量。

DeepSeek V4 通过 Token 维度压缩与 DSA 稀疏注意力降低长上下文开销；模型仍沿用 MoE 思路，仅激活部分专家，从而在能力和推理成本之间取得平衡。[cite:2][cite:4]

三、Prefix Caching 解决的是重复输入

Coding Agent 的不同请求经常共享同一段前缀：

如果前四部分在连续请求中保持不变，每次重新执行 Prefill 会浪费大量算力。Prefix Caching 会复用已计算前缀的 KV Cache，使后续请求直接从变化位置继续。

它特别适合：

  • 多轮 Coding Agent 会话；
  • 多个用户共享同一套系统提示词；
  • 固定知识库说明或工具列表；
  • 对同一份长文档提出多个问题。

但压测时必须注意缓存是否命中。vLLM 官方文档提醒，对同一服务重复运行相同数据集可能复用前一次留下的 Prefix Cache，从而虚高吞吐量。[cite:8]

四、昇腾部署不是只安装一个 Python 包

在 NVIDIA 环境中，开发者常把 CUDA、PyTorch 和 vLLM 看成一条软件栈。昇腾环境也有类似分层：

其中：

  • CANN 提供昇腾算子、编译与运行环境；
  • TorchNPU 将 PyTorch 运算映射到昇腾设备；
  • vLLM-Ascend 把 vLLM 的调度、缓存和服务能力适配到 NPU；
  • 模型服务层 暴露 OpenAI、Anthropic 等接口。

版本兼容是最容易出错的地方。驱动、CANN、PyTorch、TorchNPU、vLLM 与 vLLM-Ascend 不能随意拼接。官方预构建镜像已经包含经过验证的软件组合，通常比在宿主机逐项安装更可靠。[cite:5]

五、部署前先完成环境检查

部署前至少确认以下信息：

  1. 硬件型号和 NPU 数量
    区分 Atlas A2、A3 和推理系列产品，确认单卡片上内存。

  2. 驱动可见性
    使用 npu-smi info 检查设备、温度、健康状态和占用。

  3. 磁盘空间
    镜像、模型权重和缓存可能需要数百 GB。

  4. 网络与模型源
    无法稳定访问 Hugging Face 时，可改用 ModelScope。

  5. 端口和访问边界
    明确服务只在本机、内网还是公网暴露。

以 Atlas 800I A2 为例，官方规格为 8 个昇腾 910 模组，并提供 8 × 64 GB 或 8 × 32 GB 片上内存配置，适合大模型推理和多卡并行。[cite:7]

七、启动 DeepSeek V4 推理服务

课程实际部署的是 DeepSeek-V4-Flash W8A8 MTP 量化模型。模型文件约 300 多 GB，运行在 8 张 64 GB NPU 上，并使用 TP=8。真正启动服务时，还需要根据模型和硬件设置并行度、上下文、显存利用率与量化方式。核心命令形态如下：

这些参数不能机械照抄：

  • tensor-parallel-size 要匹配参与计算的 NPU 数量；
  • max-model-len 越大，KV Cache 预留越多；
  • max-num-batched-tokens 控制一次调度可处理的 Token 总量；
  • max-num-seqs 决定可同时调度的序列规模；
  • gpu-memory-utilization 通常可从 0.9 开始，课程也讨论了提高到 0.95，但过高可能导致运行时 OOM；
  • block-size 会影响 KV Cache 的分配粒度；
  • speculative-config 用于配置 MTP 等推测解码能力；
  • MoE 模型通常需要专家并行优化；
  • 量化类型必须与模型权重格式一致。

vLLM-Ascend 官方给出的 DeepSeek V4-Flash 量化模型可以在单台 Atlas 800 A2 或 A3 上部署，也提供多机和 Prefill/Decode 分离方案。[cite:4]

八、不要看到端口监听就认为部署成功

服务启动后，应按四层逐步验证。

1. 进程健康

2. 模型注册

检查返回的模型名是否与 --served-model-name 一致。

3. 基础推理

先使用短 Prompt 和较小的 max_tokens 验证非流式请求，再测试流式输出、长上下文和工具调用。

4. Agent 能力

最终测试不能只问知识题，还要验证：

  • 工具定义能否正确解析；
  • 工具参数是否稳定；
  • 多轮工具调用能否继续；
  • 思考内容和最终答案是否正确分离；
  • 长任务是否持续输出流式事件。

九、用正确指标做性能测试

课程使用 vllm bench 对服务进行测试。至少应该关注四类指标：

指标 含义
TTFT 从发出请求到收到首个 Token 的时间
TPOT 除首 Token 外，每个输出 Token 的平均耗时
ITL 相邻流式输出之间的延迟
Throughput 单位时间完成的请求或 Token 数

Coding Agent 更重视 TTFT 与长序列稳定性；批处理任务更重视总吞吐。单并发下的每秒 Token 数不能代表多人同时使用时的体验。

压测还要固定输入长度、输出长度、并发、数据集和缓存状态。否则两组数字没有可比性。[cite:8]

课程中的一次测试使用 100 个 Prompt，总耗时约 118 秒，吞吐约为 0.84 requests/s 和 107 tokens/s，平均 TTFT 约 557 ms，也就是约 0.557 秒。这组结果适合用来确认服务可运行，不能脱离输入长度、输出长度和并发配置与其他环境直接比较。

十、课程为什么使用 CC-Switch

Claude Code 通过 ANTHROPIC_BASE_URL 连接自定义网关时，会调用 Anthropic Messages 接口：

它还依赖流式事件顺序、工具调用字段、anthropic-version 和部分能力头。如果服务只实现 /v1/chat/completions，即使它兼容 OpenAI SDK，也不能直接被 Claude Code 使用。[cite:6]

课程部署时，vLLM-Ascend 服务暴露的是 OpenAI Chat Completions 接口。因此实际链路不是让 Claude Code 直连 8000 端口，而是在本地使用 CC-Switch：

CC-Switch 在这里承担两个职责：

  • 把 Claude Code 的 Anthropic Messages 请求转换成 OpenAI Chat Completions 请求；
  • 把 Claude Code 使用的 Sonnet、Opus、Haiku 等模型名映射到服务端注册的 DS。

新版 vLLM 已提供 /v1/messages 和 /v1/messages/count_tokens。如果所用的 vLLM-Ascend 版本、模型后端和工具调用能力都已验证兼容，也可以省去转换层，让 Claude Code 直接连接服务。[cite:9] 但这属于版本相关的替代方案，不是课程演示的接入方式。

十一、通过 CC-Switch 接入 Claude Code

首先在运行 Claude Code 的本地电脑上验证远端服务可访问：

/v1/models 能返回 DS，基础推理也正常后，再配置 CC-Switch：

  1. 新建 OpenAI Chat Completions 类型的供应商配置。
  2. 填写包含路径的完整接口 URL，例如 http://your-ascend-server:8000/v1/chat/completions。
  3. 填写 API Key。课程中的服务没有启用鉴权，因此该字段可以填任意占位值；生产环境必须配置真实鉴权。
  4. 将 Claude Code 可能使用的 Sonnet、Opus、Haiku 模型名全部映射到服务端模型 DS。
  5. 启用 CC-Switch Router，并让 Claude Code 使用该本地路由。

启动 Claude Code 后，可使用 /status 检查当前 Base URL 是否已经指向 CC-Switch 的本地 Router，然后发起一次简单对话和一次文件读取任务，分别验证文本流式输出与工具调用。

如果采用新版 vLLM 的原生 Anthropic 接口，则可以按照 Anthropic 官方文档设置 ANTHROPIC_BASE_URL 和凭证，并直接连接 /v1/messages。[cite:10] 无论使用哪种方式，密钥都不应进入项目共享的 .claude/settings.json，本地配置也应加入版本控制忽略规则。

十二、接通以后仍要验证 Agent 语义

“Claude Code 能回复”只证明协议基本可用，不代表所有 Agent 能力都正常。

还需要专门测试：

  1. 文件读取与编辑：工具调用参数是否符合 Schema。
  2. 命令执行：模型是否正确理解权限确认。
  3. 多轮工具调用：历史 reasoning_content 是否按协议保留。
  4. 长上下文：代码量增大后是否被错误截断。
  5. 中断和取消：客户端停止请求时，服务端是否释放资源。
  6. 流式输出：网关是否缓冲事件，导致界面长时间无响应。

DeepSeek 官方特别说明：思考模式下携带 tools 的多轮请求必须完整回传历史 reasoning_content，否则 API 会返回错误。[cite:3]

十三、生产部署需要补齐的边界

课程完成的是一条可运行链路。进入团队环境后，还需要补齐：

  • API 鉴权与密钥轮换；
  • TLS 和内网访问控制；
  • 用户、项目和模型级限流；
  • 请求日志与敏感字段脱敏；
  • 模型服务健康检查和自动重启；
  • 并发队列与过载保护；
  • Prometheus 指标和告警；
  • 版本升级、回滚和灰度验证。

不要直接把开发用容器和无鉴权端口暴露到公网。华为官方的一键部署参考实践也明确声明，示例需要按实际场景补充安全与可靠性加固，不建议未经处理直接进入商用环境。[cite:11]

总结

把 DeepSeek 部署到华为昇腾并接入 Claude Code，需要同时打通三层：

最容易出现的问题不是某一条命令写错，而是层与层之间的版本、协议和容量假设不一致。

更稳妥的路线是：先用官方镜像验证 NPU，再启动短上下文的最小模型服务；随后验证 OpenAI API，通过 CC-Switch 完成协议转换和模型映射，再测试流式输出与工具调用；最后才扩大上下文、提高并发并接入真实代码仓库。

当这条链路建立后，Claude Code 只是本地交互入口，真正可复用的资产是一个受控、可观测、可以被多种 Agent 客户端调用的企业推理服务。
